# AuthMod — Forge 1.20.1 server authentication

This is an MIT-licensed fork of d-society1/AuthMod (https://github.com/d-society1/AuthMod). It is intended for a small Forge server that permits offline launcher profiles.

## Commands

- /register <personalPassword> <inviteCode> — register a nickname once.
- /login <personalPassword> — unlock the current player session.
- /changepassword <oldPassword> <newPassword> — change your own password.
- /owner <allowed command> — after login, the exact configured owner may run one command with temporary permission; see restrictions below.
- /authmod changepassword <player> <newPassword> and /authmod resetpassword <player> — operator-only recovery commands.

The server owner creates authmod_invite_code.txt in the server working directory before starting Forge. The file must contain at least 16 characters and must stay private. If it is missing or unreadable, new registrations are disabled. Each player chooses a separate password of 12–120 characters by default.

Unauthenticated players are placed in spectator mode and ordinary movement, interaction, inventory drops, chat and commands other than /login and /register are blocked. They are disconnected after 300 seconds. A wrong password delays the next verification on that live connection by 1, 2, 4, then 8 seconds by default; the fifth verified wrong password kicks that connection. Attempts entered during a delay are rejected without checking the password or counting toward five. One player's failures do not lock another connection using the same nickname. A successful login resets the connection's limiter and unlocks only that player session, even when two offline nicknames differ only in letter case. The mod itself never grants persistent OP. In an isolated test, a TACZ gun-draw packet reached its handler before AuthMod login; third-party packet behavior is not fully blocked by these Forge event handlers.

New passwords are stored as salted PBKDF2-HMAC-SHA256 hashes (120,000 iterations) in authmod_data.json. The data format is compatible with earlier AuthMod versions; legacy plaintext entries are upgraded after their first successful login. Protect the data file and its parent directory with operating-system access controls and backups.

## Configuration

Forge writes world/serverconfig/authmod-server.toml for each world. The defaults are minPasswordLength=12, maxLoginAttempts=5, loginTimeoutSeconds=300, lockoutSeconds=60, maxRegisteredAccounts=256, and language=auto. Existing accounts can still log in if the count is already above the cap. Minecraft 1.20.1 limits a complete client command packet to 256 UTF-16 code units, excluding the leading `/`. New passwords are capped at 120 so `/changepassword` fits even when both old and new passwords are 120 characters. Registration additionally caps the password at `min(120, 246 - invitation length)`; the recommended 48-character invitation leaves the full 120-character password budget. Existing passwords accepted by earlier builds can still be verified up to the previous 256-character safety cap; a password of up to 250 characters fits `/login `. A user changing a longer legacy password may need to choose a shorter replacement so the full `/changepassword old new` command fits. The `lockoutSeconds` key is retained for configuration compatibility; it caps the delay on one connection and no longer locks a nickname globally.

`ownerUsername` defaults to empty. The production world sets the exact-case owner name privately and has `ops.json=[]`. After successful login, `/owner` permits only `gamemode`, `tp`, `teleport`, `give`, `time`, `weather`, `fill`, `setblock`, `summon`, `kill`, `effect`, and `gamerule`. The policy rejects nested commands, NBT, command blocks, namespaced aliases, and control characters. Account recovery remains a local console operation.

The mod is installed only on the server; its displayTest permits clients without it. It requires Forge 47.4.0+ on Minecraft 1.20.1. Use Java 17.

## Limits

Offline mode does not prove ownership of a nickname. Passwords are entered as Minecraft commands and should be unique to this server; confidentiality of those commands through the current Minecraft/Playit route has not been verified. Production now runs the codex10 JAR, whose filename retains `staging`; its owner-password login through TLauncher has not been verified. In this build, hashed `/login` checks run on at most two dedicated workers, with eight waiting checks. Each live connection has at most one pending check. A result is discarded after disconnect, session replacement, or password change. The login attempt count and delay remain per connection, never by nickname or proxy IP.

First-time `/register` hashing runs on one dedicated worker with two waiting requests. Only one pending registration is accepted per name; disconnect, clone, relock and server stop cancel it. The server thread rechecks the live session, 300-second login deadline, invitation, nickname availability, and account cap before writing the account atomically; authentication follows a successful write. Accepted hash attempts consume a server-wide in-memory budget of three immediately, one refill each 10 seconds, and 24 per rolling hour. Queue rejection refunds the budget; disconnect does not. The shared budget resets on server restart and can temporarily deny real newcomers if someone knows the reusable invitation.

Authenticated `/changepassword` verification and new hashing run on one separate worker with two waiting requests. Its own server-wide in-memory budget allows two immediately, one refill each 30 seconds, and 12 per rolling hour. The result is discarded after disconnect, clone, relock, session replacement or another password change. Registration, self-service changes, and admin reset/change save a candidate account file before changing the in-memory map. Full JSON account-file saves still run on the server thread, although rate and account caps constrain untrusted calls. Operator-only password changes and one-time legacy-password upgrades still hash on the server thread. A persistent attacker can reconnect to reset the five-attempt `/login` connection limiter, and can temporarily fill shared worker queues. Limiting failed attempts by nickname would also let an impersonator lock out the real owner in offline mode. A duplicate offline nickname can displace an existing connection in Minecraft itself. TACZ and potentially other mods accept custom packets outside AuthMod's pre-login event checks. This mod does not protect against network floods or vulnerabilities in other mods.

## Build and test

Run gradlew.bat clean build on Windows or ./gradlew clean build on other systems with JDK 17. Gradle downloads the Forge toolchain. The reobfuscated JAR is written to build/libs/authmod-1.5.2-codex10-staging.jar; regression tests run as part of build. The codex9 login queue and codex10 registration/password change were exercised on an isolated loopback 25590 Forge stage with disposable clients. Codex10 tests cover queue capacity/cancellation, budget refill, transactional account writes, and failed saves. The stage client registered, received an invalid-invite rejection after a stage-only account reset, registered again, disconnected, reconnected and logged in. It also tried a wrong old password for `/changepassword`, then changed to a new password; after reconnect, the old password failed and the new one succeeded. A prior synthetic account remained in the data file. The stage is stopped. After a verified cold backup, production loaded the codex10 JAR without startup errors; RCON reported zero players, the authentication file's byte hash was unchanged, and the Playit tunnel accepted a TCP connection. These checks do not verify an owner password login or third-party packet restrictions.
